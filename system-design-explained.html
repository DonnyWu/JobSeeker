🏗️ JobSeeker — how the whole system fits together

A guided tour of the architecture, written for a junior dev

TL;DR — JobSeeker is a Streamlit web app that helps you find jobs, score how well they match your résumé using an AI model (Groq), and auto-fill applications with a real browser (Playwright). It has three layers: the screens you click (pages/), the brains that do the work (src/), and a small SQLite database that remembers everything. Data flows in a loop: you click → logic runs → results land in the database or memory → the screen redraws.

1. What the app actually does

Think of JobSeeker as a personal job-hunting assistant with four jobs:

  • Remember you — your contact info and your parsed résumé.
  • Find jobs — scrape several job boards at once for a search you type.
  • Rank them — ask an AI to score each posting against your résumé like an ATS (Applicant Tracking System — the keyword robot recruiters use to filter résumés).
  • Help you apply — open the application in a real browser, pre-fill your details, and track what happened afterward (the new Applied tab).

4. The screens — how Streamlit pages work

Streamlit has a rule: any .py file inside a pages/ folder automatically becomes a screen in the left sidebar, and the leading number sets the order. That's the whole routing system — no router code to write.

⭐ Big idea — the rerun model

Streamlit re-runs the entire page script from top to bottom every time you interact with it. There's no "onClick handler that surgically updates one widget." So how does anything persist? Two places: (1) st.session_state — a dictionary that survives reruns within your session (used for the search results table and the currently-selected job), and (2) the SQLite database — survives even after you close the app. Everything you see on screen is just a fresh drawing of that saved state.

5. The data layer — one database, four tables

All persistence is SQLite (a database that's just a single file, data/jobseeker.db). Every read and write goes through one module, src/profile_manager.py — think of it as the only door into the database. Pages never write SQL themselves. Here are the four tables:

profile
  • id · PK
  • name, email, phone
  • current_company
  • linkedin, portfolio, github
resume
  • id · PK
  • file_name, raw_text
  • skills, experience (JSON)
  • education (JSON), summary
  • total_years_experience
saved_jobs
  • id · PK
  • title, company, location, url
  • match_score, match_reason
  • status saved | applied
  • job_key dedup key
  • outcome, interview_stage
  • applied_at (new!)
search_prefs
  • id · PK
  • query, location
  • time_filter, is_remote
  • min_score

The purple fields on saved_jobs are the ones the Applied-tab feature added. Notice there are no foreign keys joining tables — it's a small, single-user app, so each table stands alone. The clever bit is job_key: a normalized company|title|city string so the same role from LinkedIn and Indeed is recognized as one job.

⭐ Big idea — single source of truth

Funnelling all DB access through profile_manager.py means table shapes, the dedup logic, and migrations live in exactly one place. When we added 3 columns for the Applied tab, only that file and the migration changed — the pages didn't care. That's the payoff of a clean data layer.

6. Flow A — Onboarding (profile & résumé)

Before you can score jobs, the app needs to know you. The résumé path is the interesting one — a file becomes structured data an AI can compare against:

UploadPDF / DOCX
→
extract_textpdfplumber / docx
→
parse_resumeGroq LLM → JSON
→
save_resumeinto resume table

The raw file is dumped into uploads/, its text is extracted, then the LLM is asked to return strict JSON: a summary, skills list, experience, education, and an estimated total_years_experience. That years-of-experience number later powers the seniority fit part of scoring. The profile form is much simpler — it just upserts one row into the profile table.

7. Flow B — Search & AI scoring (the heart of the app)

This is the most interesting flow. Here's what happens when you hit Search:

Scrape — job_scraper.scrape_jobs()

jobspy hits LinkedIn, Indeed, Glassdoor, ZipRecruiter & Google in one call and returns a pandas DataFrame of postings.

Filter to your location

The boards (especially Google) leak out-of-state results, so a regex/state-abbreviation filter trims them down — while still keeping genuinely remote roles.

Score against your résumé — job_matcher.rank_jobs()

Jobs are split into batches of 5 and sent to Groq concurrently (up to 8 at once) using a ThreadPoolExecutor, because each batch is a slow network call.

Blend the sub-scores into one number

The model returns component scores; the app (not the model) blends them with fixed weights, so scoring is deterministic and tunable. See the formula below.

Sort & stash → render cards

The ranked DataFrame is saved into st.session_state.results_df so it survives reruns, then drawn as cards filtered by your "minimum match score" slider.

The scoring formula, visualized

The AI rates four things 0–100. The final score is a weighted average:

coverage · 50%
seniority

title
fit · 15%

fit · 15%

…then a safety rule: if the posting states a hard requirement you clearly fail (a "knockout" — e.g. "10+ yrs required" but your résumé shows ~5), the score is capped at 40 no matter how good the rest looks. Bars wider = counts more. The biggest signal is keyword coverage, exactly like a real ATS. 

# src/job_matcher.py — the blend is plain Python, not the model's opinion
score = round(
    0.50*ats_coverage + 0.20*seniority_fit + 0.15*title_fit + 0.15*education_fit
)
if knockouts:                 # failed a hard requirement?
    score = min(score, 40)     # cap it
⭐ Big idea — let the AI judge, but you do the math

The LLM is great at reading a job description and rating fuzzy things ("how senior is this role?"). It's bad at consistent arithmetic. So the design asks the model only for the sub-scores, then computes the final number in code with temperature=0. Result: the same job always gets the same score, and you can re-tune the weights without re-prompting the AI.

Failure handling (a recurring theme)

If a batch's API call fails, that job's score becomes None — not 0 — so a network blip isn't mistaken for "terrible match." Only if every batch fails does the app raise a real error telling you to check your API key. This "fail soft, surface the truth" pattern shows up all over the codebase (e.g. company_insights never raises — it just returns an empty summary).

8. Flow C — Apply & track the outcome

From a job card you click Auto-Apply, which carries you to the Apply screen and then to a real browser:

→
save_jobstatus = saved
→
Apply pagevia session_state
→
Playwrightopens Chromium, fills fields, pauses
→

→

The auto-fill is deliberately human-in-the-loop: autofill.py matches each form input to your profile by keywords, fills what it can, then calls page.pause() so you review and click Submit. It never submits on your behalf. Once you mark a job applied, it appears on the new Applied tab, where the outcome / interview_stage columns let you track Interview → Offer → Accepted / Declined — the raw material for analytics later.

9. Big ideas worth stealing from this codebase

  • Layered separation. UI (pages/) only draws and gathers input; logic (src/) does the work; one module owns the database. You can rewrite a page without touching business logic, and vice-versa.
  • State is the truth, UI is a function of it. Because Streamlit reruns everything, you never "update the screen" — you update session_state or the DB and let the rerun redraw.
  • A DataFrame as the shared spine. Jobs stay in one pandas table from scrape → filter → score → render. New columns (scores, skills) are just added to it.
  • Deterministic where it matters. AI for judgment, plain Python (temperature=0 + fixed weights) for the final number.
  • Fail soft, but never silently lie. Missing data becomes None/empty, not a fake 0; best-effort features swallow errors; but a totally-broken API key raises a clear message.
  • Concurrency only where it pays. Network-bound scoring batches run in a thread pool; everything else stays simple and synchronous.
  • Additive change. The Applied feature added columns instead of repurposing status, so nothing old broke — and the 48 existing tests still passed.
⚠️ One gotcha to know

Secrets load from .env via load_dotenv() once, at startup. If you paste a new GROQ_API_KEY while the app is running, it won't take effect until you restart the app — load_dotenv() won't overwrite a value it already loaded. (This is the exact bug documented in bug-explained.html.)
