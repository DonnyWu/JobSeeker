🔬 JobSeeker — a deep dive, in diagrams

For a junior dev. Four guided tours: a search request, the AI scoring, the data, and the whole map.

TL;DR — This doc explains how the moving parts actually move, using four kinds of diagram. We trace one search click end-to-end, open up the AI scoring engine, map the database, and re-draw the whole architecture — all as real Mermaid diagrams (the same text renders on GitHub too).
How to read the diagrams (3 shapes, that's it):
  • Flowchart — boxes are things/steps, arrows mean "leads to / calls". A diamond ◇ is a yes/no decision.
  • Sequence diagram — each vertical line is one actor/module; time flows downward; arrows are messages/calls between them. A solid arrow is a call, a dashed arrow is the reply.
  • ER diagram — each box is a database table and its columns.

⭐ Why a DataFrame?

One pandas table (the "DataFrame") is the spine the jobs ride on the whole way: scrape fills it, the location filter trims rows, scoring adds columns (match_score, missing_skills…), and the UI reads rows to draw cards. Passing one table around beats juggling loose lists.

2Inside the AI scoring engine job_matcher.py

This is the cleverest part of the app. The question it answers: "how well does this résumé match this job, the way a recruiter's ATS robot would judge it?" Here's the journey of one job through scoring:

flowchart · how one job becomes a 0–100 score 
flowchart TD
  RES["Your résumé
skills · years · experience"] --> PROF["Build candidate
profile text"]
  JOB["Job posting
title + description"] --> PROMPT
  PROF --> PROMPT["Prompt sent to Groq
temperature = 0 (deterministic)"]
  PROMPT --> LLM(["🤖 Groq LLM"])
  LLM --> JSON["Returns JSON sub-scores:
ats_coverage, title_fit,
seniority_fit, education_fit,
knockouts, reason"]
  JSON --> BLEND["Blend in PYTHON, not the AI:
0.50·ATS + 0.20·seniority
+ 0.15·title + 0.15·education"]
  BLEND --> CAP{"Posting has a hard
requirement you fail?"}
  CAP -->|yes, knockout| CAPPED["score = min(score, 40)"]
  CAP -->|no| FINAL["⭐ Final score 0–100"]
  CAPPED --> FINAL

The weights, and why the app (not the AI) does the math

The model is great at reading a job and rating fuzzy things ("how senior is this?"). It's unreliable at consistent arithmetic. So we ask it only for the four sub-scores, then combine them in plain Python. temperature=0 makes the model's answers stable, and fixed weights mean the same job always gets the same number — and we can re-tune without re-prompting. 

# the keyword-coverage signal dominates — exactly like a real ATS
_WEIGHTS = {"ats_coverage":0.50, "seniority_fit":0.20, "title_fit":0.15, "education_fit":0.15}
_KNOCKOUT_CAP = 40   # fail a must-have → can't score above this

Doing it fast: batching + concurrency

Scoring 50 jobs one-by-one would mean 50 slow network round-trips. Instead jobs are grouped into batches of 5, and the batches are sent to Groq at the same time using a thread pool (up to 8 in flight). The results are gathered back in the main thread and sorted.

⭐ Fail soft, never lie

If one batch's call fails, those jobs get a score of None (unknown) — not 0 — so a network hiccup isn't mistaken for "terrible match". Only if every batch fails does the app raise a loud error pointing at your API key. That distinction (unknown vs. zero) is a small thing that saves a lot of confusion.

The job_key trick — recognizing the same job twice

The same role shows up on LinkedIn and Indeed with different URLs. To avoid duplicates, every job gets a job_key: a normalized company|title|city string. Save the "same" job again and it updates one row instead of creating a second. 

job_signature("Acme Corp ", "  Software  Engineer", "Boston, MA, US")
   # → "acme corp|software engineer|boston"  (lowercased, spaces collapsed, city only)

What survives a rerun vs. a restart?

Remember Streamlit re-runs the whole script on every click. So "where does my data live between clicks?" is the key question. There are two memories with different lifespans:

⭐ One door to the database

Every read/write goes through profile_manager.py. Need a new column? You change the table shape, the dedup logic, and the migration in one file — pages don't care. That's exactly why the Applied-tab change (3 new columns ★) touched the data layer and nothing else broke.

Migrations — upgrading a database that already has your data

Your jobseeker.db already exists with the old shape. You can't just change the CREATE TABLE text — that only runs for a brand-new file. So at startup the app asks the table which columns it has and adds any missing ones. It's idempotent: safe to run every launch, only adds each column once. 

# runs in init_db() on every startup
sj_cols = [c for c in existing_columns("saved_jobs")]
for col in ("outcome", "interview_stage", "applied_at"):
    if col not in sj_cols:
        ALTER_TABLE_ADD_COLUMN(col)   # add it just once

4Bonus: the apply & track flow

Finally, what happens from clicking Auto-Apply on a card to recording an outcome on the new Applied tab. The important detail: the browser auto-fill is human-in-the-loop — it fills fields then pauses so you review and submit yourself. It never submits for you.

sequenceDiagram · apply, then track the result 
sequenceDiagram
  autonumber
  actor You
  participant JS as Job Search
  participant PM as profile_manager
  participant AP as Apply page
  participant PW as Playwright / Chromium

  You->>JS: click Auto-Apply on a job
  JS->>PM: save_job (status = saved)
  JS->>AP: open Apply page (job in session_state)
  You->>AP: click Launch Auto-Fill
  AP->>PW: open Chromium, fill matching fields
  PW-->>You: PAUSE — review before submitting
  You->>PW: click Submit yourself
  You->>AP: click "I've applied — mark it"
  AP->>PM: mark_job_applied (status = applied, stamp applied_at)
  You->>AP: Applied tab → press Interview / Offer / Declined
  AP->>PM: update_application_outcome (+ interview stage)

Steps 8–10 are the feature we added: a job stays status = applied forever (so the Job-Search "Applied" badge keeps working), while the new outcome column tracks what happened next — the raw data for the analytics you're planning.
