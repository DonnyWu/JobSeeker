Why job scoring is slow, and why it keeps hitting the limit

A measured look at src/job_matcher.py and the Groq free tier — and the six fixes that follow from it.

TL;DR — It is not really the model. Your app asks the AI to grade 100 jobs by firing 20 requests, 8 of them simultaneously, at an account that allows 8,000 tokens per minute. The requests that bounce are the jobs that come back saying “couldn’t be scored”, and nothing retries them.

On top of that, the model has been silently writing a hidden internal monologue before every answer, the same 1,480 tokens of instructions get re-sent 20 times per search, and no score is ever remembered. Fixing those four things takes a fresh search from ~132,000 tokens to ~33,000, and makes repeat searches nearly free.

What you actually see

Two symptoms, which turn out to have overlapping causes:

  • A search takes a long time, with nothing on screen until the whole thing finishes.
  • Some jobs come back with no score and a warning: “N job(s) couldn’t be scored and aren’t shown.”

The second one is already half-diagnosed in your own code. From pages/3_Job_Search.py:527-530:

# Jobs the scorer never managed to grade. rank_jobs only raises when
# *every* batch fails, so a partial failure — Groq rate-limiting a few of
# the twenty batches a 100-job chunk fires off — leaves rows with no score

That comment is correct. This page is about why those batches get rate-limited, and what to do about it.

Where the 20 comes from: pages/3_Job_Search.py:34 sets _SCORE_CHUNK = 100, and src/job_matcher.py:20 sets _BATCH_SIZE = 5. One hundred jobs at five per request is twenty requests. src/job_matcher.py:37 sets _MAX_WORKERS = 8, so eight of them leave at once.

Cause 1 — The flood

This is the one that produces the unscored jobs. Think of the rate limit as a pipe. Groq’s free tier gives you a pipe sized for 8,000 tokens a minute. Your app dumps a bathtub into it in the first second.

Why it isn’t caught

Two separate gaps. First, src/job_matcher.py:395-400 catches a failed batch, records it, and moves on — rank_jobs only raises if every batch fails. A partial failure is silent. Second, _scoring_error_message at pages/3_Job_Search.py:349-374 branches on 403 and 401 but not 429, so a rate limit falls through to a generic “check that your GROQ_API_KEY is valid” — sending you to re-check a key that was never the problem.

Cause 2 — The model is thinking out loud

This is the biggest contributor to slowness, and it is invisible.

openai/gpt-oss-120b is not a plain chat model — it is a reasoning model. Before producing an answer it writes out an internal monologue you never see. How much it writes is controlled by a parameter called reasoning_effort, and Groq’s API reference is explicit about the default:

// Groq API reference — reasoning_effort
"openai/gpt-oss-20b and openai/gpt-oss-120b support 'low', 'medium',
 or 'high'. 'medium' is the default value."

Your code never sets it. Every one of those 20 calls per search has been running at medium effort, generating hidden text that you wait for and that counts against your quota.

Fix — on scoring only. Pass reasoning_effort="low" in _score_batch at src/job_matcher.py:197. That is the call that runs 20× per search, and it holds essentially all of the cost.

Leave the other three call sites at the default. Each fires once, rarely, and output quality matters more there than token cost:

Call siteHow oftenSettingWhy
_score_batch :19720× per searchlowAll the cost is here; mostly extraction
generate_why_interested :3341× per clickdefaultA human employer reads this text
resume_parser.py:781× per uploaddefaultFeeds every downstream score

Make it env-overridable (GROQ_SCORING_EFFORT, default low) so the tradeoff can be tested without a code edit.

Does lower effort make the matching worse?

It might, on some fields. The blended score is not uniformly reasoning-dependent, so the risk is uneven:

FieldWeightWhat it needsRisk
ats_coverage50%Pull keywords, check presence in the résuméLow — mechanical
title_fit15%Compare title to backgroundLow
education_fit15%Check stated degree requirementsLow
seniority_fit20%Infer total years, judge level above/belowMedium
knockoutscaps at 40Decide which hard requirements genuinely failMedium–high

Roughly half the score is keyword matching and should barely move. The judgment-heavy parts are where degradation would show up if it shows up at all.

One security consideration. The scorer also returns an injections field — the model reporting when a posting contains hidden instructions aimed at an AI reader. That is a security signal, and it is one of two independent detectors; src/job_matcher.py:446-449 merges it with the regex results from jd_shield.

Lower reasoning effort could plausibly make the model less likely to spot a subtle one. The regex shield still runs either way, so this is defense-in-depth rather than a single point of failure — but check it explicitly when comparing before and after.

This is a hypothesis about the shape of the task, not a measured result. Nobody has run these prompts at low versus medium effort yet. Before trusting it: dump the scored frame to CSV, change only reasoning_effort, re-run the same query, and join on job_key to compare. Because temperature=0 is already set at :200, any difference is caused by the effort change rather than sampling noise.

Watch knockouts first — losing one moves a job from “correctly filtered out” to “looks like a match.” If quality drops, set GROQ_SCORING_EFFORT=medium and keep everything else. The batch-size change and the score cache deliver most of the token savings on their own; the reasoning setting is the speed win, and it is the one worth giving up if it costs accuracy.

Cause 3 — The same text, twenty times

Every batch is built the same way in src/job_matcher.py:190-195: scoring instructions, then the safety guard, then your résumé profile, then the five job descriptions. Only the last part changes between batches. The first three are byte-identical every single time.

Fix — raise _BATCH_SIZE from 5 to 12 and _MAX_TOKENS from 2500 to 5000. Add an explicit truncation check before parsing, because the failure mode gets more expensive as batches grow:

if response.choices[0].finish_reason == "length":
    raise RuntimeError("scoring reply truncated — raise _MAX_TOKENS or lower _BATCH_SIZE")

Without that check, a truncated reply surfaces as a confusing JSON parse error rather than telling you what actually went wrong.

Cause 4 — Nothing is ever remembered

Your database has four tables: profile, resume, saved_jobs, search_prefs. None of them stores a score. There is no in-memory cache either — no @st.cache_data, no lru_cache on the scoring path.

So searching “Python developer” today and again tomorrow means paying full price for the large overlap between the two result sets. Job boards return substantially the same postings day to day; you are re-grading them every time.

Fix — a score_cache table, using job_signature() from src/jobkey.py:17, which already exists for board dedupe and saved jobs.

Two details worth getting right the first time.

Key on the résumé text, not resume.id. save_resume at src/profile_manager.py:163 always INSERTs a new row, so keying on the id would throw away the whole cache every time you re-upload the same file. Hashing the rendered profile invalidates exactly when the prompt actually changes.

Include a scorer_version. Without it, editing _SCORING_INSTRUCTIONS or _WEIGHTS would keep serving scores computed under the old rubric forever.

One line must change or a perfect result reports as a failure. src/job_matcher.py:402 reads if succeeded == 0: raise. Once caching lands, a fully-cached search runs zero batches — so succeeded is 0 and it raises “scoring failed” on a search where everything worked. It has to become if batches and succeeded == 0:.

What the whole flow looks like after

The two fixes that cost nothing to run

Don’t grade jobs that obviously don’t fit

Before spending a single token: drop jobs you have already applied to (get_applied_keys() already exists at src/profile_manager.py:307), roles far above your experience level, and postings with no title overlap with your query. Roughly 100 → 40 jobs worth grading.

This should be skip-only, never delete — filtered jobs stay visible with a note, and there is a sidebar toggle to turn it off, so an unusually-titled job you would have liked is never silently lost.

Stop waiting on boards that always fail

From streamlit.detached.err.log, on every run going back months:

ERROR - JobSpy:ZipRecruiter - ZipRecruiter response status code 403
ERROR - JobSpy:Glassdoor   - Glassdoor response status code 400
ERROR - JobSpy:Glassdoor   - Glassdoor: location not parsed

Two of your five boards return nothing, every single time, and you wait for them before any AI work begins.

Scraping depth — already fixed

src/job_scraper.py:323 requested results_wanted = 150 per board, per location — over 750 rows for a single city when only 100 ever get scored. Traced to PR #15, which raised it from 50 to 150. The commit message describes the user-facing goal and never mentions the bump; it is visible only in the diff.

At the time it made sense, because scoring had no cap — deeper scraping meant more scored jobs. Then the multi-location commit introduced _SCORE_CHUNK = 100 and the depth stopped reaching the user. The extra ~500 rows just sat in pending_df.

What they did cost was wall-clock. _scrape_board walks locations sequentially within each board — deliberately, to avoid tripping the boards’ rate limiters — while the five boards run in parallel. So the scrape is the slowest part of a search, and it scaled directly off this number.

Lowering 150 → 50Effect
Scraping wall-clock~3× faster
Tokens per Search clickno change — capped at 100 jobs either way
Tokens overallindirectly lower — smaller pile, fewer More Jobs clicks to spend on

Fifty still fills a 100-job chunk comfortably: five boards × 50 is roughly 250 rows for one city before dedupe. Changed, and all 317 tests pass.

Multi-location is not the token problem. It came up as a suspect and is worth clearing. Tokens per Search click are identical whether you search one city or three, because _SCORE_CHUNK caps scoring at 100 jobs regardless. What it costs is scraping wall-clock — roughly 3× for three cities, since locations are walked in sequence per board.

It is also the commit that introduced _SCORE_CHUNK in the first place: the brake that stopped PR #15’s 750-row hauls from being scored in one go, which would have been ~150 batches and roughly 810,000 tokens on a single click — four times the entire daily free-tier allowance. Worth keeping.

The honest caveat. On the free tier a search will take 3–4 minutes, because the pacer deliberately slows down to fit inside 8,000 tokens per minute. It finishes instead of failing, and results appear progressively so it does not feel like a dead spinner — but it is not fast. The thing that makes it ~15 seconds is a larger token allowance, and the code is written so that switching costs nothing but a payment method.

Order of work

  1. Quick wins — reasoning_effort, structured JSON output, bigger batches. Best effort-to-impact ratio.
  2. Score cache — biggest win for how the app is actually used.
  3. Pacing and retries — makes the dropped-job failures stop.
  4. Progressive rendering — biggest change in how fast it feels.
  5. Pre-filter — most tuning required, so it comes after the safe wins.
  6. Scraping cleanup — independent of everything else.

Each step leaves the app working. Steps 1 and 2 deliver most of the benefit.

One thing to verify during implementation. Groq’s reasoning documentation and their API reference contradict each other on whether reasoning_format can be combined with JSON mode. Test reasoning_effort="low" together with structured outputs first. If they conflict, keep structured outputs and fall back to prose JSON instructions — the reasoning setting is the more valuable of the two.

What this deliberately does not change

  • The provider. Staying on Groq. Nothing here is Groq-specific enough to block a future move — the cache, the pre-filter, and the pacer would all carry over.
  • The model. openai/gpt-oss-120b stays. src/llm.py:27-30 documents why the alternatives were rejected, and the problems measured here are architectural, not model quality.
  • The injection defenses. src/jd_shield.py, the fencing, the data guard, and the canary-token output checks in generate_why_interested all stay exactly as they are. Moving the instructions into a system message strengthens that boundary rather than weakening it.
