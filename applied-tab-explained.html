✅ The "Applied" tab — what changed & why

JobSeeker · commit 2ef18fe · explained for a junior dev

TL;DR — We added a second tab on the Apply page called Applied. It lists every job you've marked as applied, and gives each one four buttons — Interview / Offer / Accepted / Declined — plus a free-text box to note which interview round you're on. To remember those answers between sessions we added 3 new columns to the database and 2 helper functions. We were careful to add new fields instead of changing the existing status field, so nothing that already worked broke. 3 files changed, 52 tests still green.

The 30-second mental model

JobSeeker is a Streamlit app. Two things are worth knowing before reading the code:

  • Each file in pages/ is a screen in the left sidebar (Profile, Resume, Job Search, Apply). We did not add a new sidebar screen.
  • Inside one screen you can have tabs (like browser tabs). Our "Applied" view is a tab inside the existing Apply screen — that's what "another tab under the apply section" meant.
  • The golden rule of Streamlit: every time you click anything, Streamlit re-runs the whole script from top to bottom. The screen is just a function of your data. So the pattern is always: click button → save to DB → re-run → read DB → draw fresh UI. Keep that loop in your head and the code reads easily.

The big idea: store the outcome next to the status, not in it

The database already had a status column on each saved job, holding either 'saved' or 'applied'. The tempting shortcut was to just add more values to it: 'interview', 'declined', etc. We deliberately did not do that. Here's why:

✗ Tempting shortcut

Reuse status: set it to 'interview' or 'declined'.

Problem: other code already trusts status == 'applied' — the "Applied" badge in Job Search, and a test that says an applied job can never be downgraded. The moment you set it to 'declined', that job stops counting as applied and the badge disappears. You'd silently break two existing features.

✓ What we did

Leave status alone. Add a separate outcome column.

A job stays status='applied' forever (so the badge + tests keep working), and outcome tells the new story: interview, offer, accepted, or declined. Two independent facts → two columns.

⭐ Lesson

Prefer additive changes. When a column already has other code depending on its meaning, don't overload it with new meanings — add a new column. Your change becomes "purely additive": old behaviour is untouched, so the blast radius of a bug is tiny.

② A "migration" so old databases don't crash

Your data/jobseeker.db file already exists with the old shape. Just changing the CREATE TABLE text wouldn't add columns to a table that's already there. So in init_db() we check what columns exist and add any that are missing. This runs every startup and is idempotent — safe to run a hundred times, it only adds a column once. 

# runs at startup; PRAGMA table_info tells us which columns already exist
sj_cols = [r[1] for r in conn.execute(text("PRAGMA table_info(saved_jobs)")).fetchall()]
# Post-application outcome tracking (added to older databases).
for col in ("outcome", "interview_stage", "applied_at"):
    if col not in sj_cols:
        conn.execute(text(f"ALTER TABLE saved_jobs ADD COLUMN {col} TEXT"))
        conn.commit()

We copied this exact pattern from the existing job_key migration two lines above — matching the code that's already there is almost always the right call.

③ Stamp applied_at the first time a job becomes "applied"

Inside _upsert_job() (the one function that writes a job row) we set the timestamp once, and never overwrite it — so if the same job gets touched again later, the original apply date survives. 

if payload["status"] == "applied" and not applied_at:
    applied_at = datetime.utcnow().isoformat()   # only when it's empty

② The one sneaky bug we had to avoid: st.stop()

The old page started with: "if no job is selected, show a message and st.stop()." But remember the golden rule — Streamlit runs the whole file top to bottom. st.stop() doesn't just stop that tab; it kills the entire script run. If we'd left it in, opening the page with no job selected would have stopped before the Applied tab ever got drawn — so your new tab would mysteriously vanish in some cases.

✗ Before

if not job:
    st.info("No job selected…")
    st.stop()  # kills everything

✓ After

with tab_apply:
    if not job:
        st.info("No job selected…")
    else:
        ... # show the form

Same user experience, but using if/else instead of st.stop() keeps the message scoped to just that tab.

③ Draw the list, one card per applied job

We loop over get_applied_jobs() and reuse the exact card style from the Job Search page (st.container(border=True) + columns). For each job: a badge showing its current outcome, then four buttons. Clicking a button follows the golden-rule loop: 

if b1.button("🎯 Interview", key=f"oc_interview_{jid}"):
    update_application_outcome(key, "interview")   # 1. save to DB
    st.rerun()                                    # 2. re-run → list redraws with new badge
⭐ Lesson

Every button needs a unique key (we used the job's id: f"oc_interview_{jid}"). If two buttons share a key, Streamlit thinks they're the same widget and they fight each other. Unique keys per row is the standard fix when you render a list of interactive widgets.

④ The conditional input — only show the stage box when you're interviewing

if outcome == "interview":                 # only render this when relevant
    stage_input = st.text_input("Current interview stage",
                                value=job.get("interview_stage") or "", ...)
    if st.button("Save", key=f"savestage_{jid}"):
        update_application_outcome(key, "interview", stage_input)
        st.rerun()

The box is seeded with whatever you typed before (value=...), so it survives reloads. This is exactly the feature you asked for: "if I got an interview, let me note what stage I'm on."

File 3 — the safety net tests/test_profile_manager.py

We added 4 small tests. Each runs against a throwaway database in a temp folder (a pytest fixture swaps the real DB for a fresh one), so tests never touch your real jobseeker.db and don't need internet or API keys.

  • get_applied_jobs returns only applied jobs (a "saved" one is excluded) and includes the new columns.
  • Recording an outcome with a stage saves both values.
  • Recording a later outcome without a stage leaves the old stage untouched (the guard from Lesson 2).
  • applied_at gets stamped, and a later save does not clear it.
Result: pytest → 52 passed. The 48 old tests still pass (proving we didn't break anything) and our 4 new ones lock in the new behaviour. all green

What's next (so you know the shape of it)

Right now each job stores a single current outcome (e.g. it's "interview", then becomes "offer"). For the analytics feature you mentioned, if you ever want a full timeline — "applied on the 1st, phone screen on the 5th, onsite on the 12th" — that would be a separate application_events table (one row per event with a timestamp). The applied_at column we added today is the first breadcrumb toward that.
