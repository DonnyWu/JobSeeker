📍 How we added a “search radius” to Job Search

JobSeeker · a walkthrough of the distance-slider feature, written for a junior dev

TL;DR — Job Search used to filter results by matching the state name in text (“is this job in Massachusetts?”). That’s all-or-nothing per state and has no idea of how far a job is. We added a 0–100 mile slider that filters by real geographic distance, so a search from New York can pull in nearby New Jersey and Connecticut jobs by distance — crossing state lines — while still cutting far-away ones. Under the hood we turn each location into latitude/longitude and measure the great-circle distance.

The old way: matching location text the limitation

When you searched, the boards (especially Google) leak jobs from all over the country. To clean that up, the app kept only rows whose location text mentioned your state or city. Roughly:

src/job_scraper.py — the text filter (still here, still useful)

def _row_matches(row_loc, names, abbrevs):
    # keep the job if its location text contains "Massachusetts"
    # or the whole token "MA"
    ...
    return any(n in row_loc for n in names)

This works, but it’s a yes/no on the whole state. It can’t answer the question people actually have when job-hunting: “show me anything within a reasonable commute.” Two concrete problems:

  • 🚫 No distance knob. You couldn’t say “only within 25 miles” or “stretch to 100.”
  • 🚫 Stops at the border. If you live in New York City, tons of great jobs are a short drive away in New Jersey or Connecticut — but a text filter for “New York” throws them all out, even ones closer than jobs upstate in your own state.

What a “radius” actually means

A radius is a circle drawn around where you are. Anything inside the circle is “close enough.” The slider sets how big the circle is. Notice how the circle happily spills over state borders — that’s the whole point.

inside the radius — kept outside — dropped you / 100-mi ring 25-mi ring

At 100 miles, Newark (9 mi) and Stamford (34 mi) are in — even though they’re in different states — but Boston (190 mi) is out. Drag the slider down to 25 miles and Stamford drops too, while Newark stays. That’s exactly what the feature does.

Two layers do the work

The radius is enforced in two places — a rough first pass, then a precise trim:

Layer 1 · the job boards (rough, server-side)
We pass the slider value straight into jobspy as its distance argument. Indeed/LinkedIn/Glassdoor/ZipRecruiter do their own radius search and return a roughly-near-you batch. Fast, but each board interprets it loosely.
↓boards hand back a messy pile that’s approximately in range
Layer 2 · our code (precise, client-side)
✓We re-check every job ourselves with real math (_filter_by_radius) and keep only the ones truly within the miles you asked for. This is what makes the slider exact and consistent across all boards.
💡 Jr dev note — why not trust the boards alone? Each board treats “distance” differently, and Google barely respects it at all. If we relied only on Layer 1, “50 miles” would mean something different on every site. Doing our own check in Layer 2 means one definition of distance for everything — and it’s easy to unit-test because it’s just Python math, no network.

Step 1: turn an address into coordinates (“geocoding”)

To measure distance you need numbers, not the words “Newark, NJ.” Geocoding is looking up a place’s latitude and longitude (its dot on the globe). We do it offline using a bundled dataset called geonamescache — no internet call, no API key.

src/geo.py

geocode("Newark, NJ")  ->  (40.736, -74.172)   # (latitude, longitude)
geocode("Remote")      ->  None                  # not a real place we can pin
geocode("United States")-> None                  # too vague to place
💡 Jr dev note — a sneaky bug we hit “New York” is both a city and a state. Our first parser scanned the words and saw “New York,” decided it was the state, and lost the city. The fix: always treat the first comma-part as the city ("New York") and only look for a state in what’s after the comma ("NY"). Little parsing gotchas like this are extremely common — write a test the moment you find one. (We did: see tests/test_geo.py.)

Step 2: measure the distance between two dots

You might think “just subtract the coordinates.” But the Earth is a ball, not a flat sheet, so a straight subtraction is wrong — especially over long distances. The standard fix is the haversine formula, which measures the distance along the curved surface of the globe.

src/geo.py → haversine_miles()

def haversine_miles(a, b):                 # a, b are (lat, lon) pairs
    lat1, lon1 = math.radians(a[0]), math.radians(a[1])
    lat2, lon2 = math.radians(b[0]), math.radians(b[1])
    dlat, dlon = lat2 - lat1, lon2 - lon1
    h = math.sin(dlat/2)**2 + math.cos(lat1)*math.cos(lat2)*math.sin(dlon/2)**2
    return 2 * EARTH_RADIUS_MILES * math.asin(math.sqrt(h))
💡 Jr dev note — you don’t need to memorize this Think of haversine as a black box: feed it two (lat, lon) dots, it returns the miles between them as if you walked along the Earth’s surface. The trig (sin/cos) is just the math for “distance on a sphere.” The important habit is recognizing when you need it — any time you’re measuring real-world distance from latitude/longitude.

Putting it together: the keep-or-drop decision

For each job row, _filter_by_radius asks three questions in order:

Is the job remote? (the location text says Remote / Anywhere / WFH)
→ KEEP. Remote has no distance; we never want to hide it.
↓ not remote…
Can we geocode the job’s “City, ST”?
→ Measure it. haversine ≤ radius ? KEEP : DROP.
↓ can’t geocode it (a small town, a bare state, “United States”)…
Fallback · use the old text filter
→ Keep it only if it’s in the state you typed. This preserves the original anti-leak behavior (Maine/Texas jobs still get cut when you search “MA”).

src/job_scraper.py → _filter_by_radius()

origin = geocode(location)
if origin is None:                 # you typed just a state, e.g. "MA"
    return _filter_by_location(jobs, location)   # a radius is meaningless -> old behavior

def _within(text):
    pt = geocode(text)
    if pt is not None:
        return haversine_miles(origin, pt) <= radius_miles   # the precise check
    return _row_matches(text, names, abbrevs)            # fallback: in-state text match

return jobs[loc.apply(_within) | _remote_mask(loc)]
💡 Jr dev note — “superset”, and why nothing broke The new filter is a superset of the old one: when it can’t measure distance, it falls back to exactly what the app did before. That’s why all the original location tests still pass — we added capability without changing the old guarantees. Building features this way (extend, don’t replace) keeps risk low.

The slider, and remembering it

On the Job Search page the control is a normal Streamlit slider sitting under the Location box. Default is 50 miles; 0 means “this city only.”

pages/3_Job_Search.py

distance = st.slider("Search radius (miles)", 0, 100, default, step=5, ...)
...
raw = scrape_jobs(query, location, time_filter, is_remote=is_remote,
                 distance_miles=distance)

Just like the other search inputs, the slider value is saved so it survives a browser refresh. We store it in the search_prefs table. Older databases don’t have the new column, so init_db() quietly adds it the first time the app starts:

src/profile_manager.py → init_db()

# Lightweight migration: add the radius column to older databases.
sp_cols = [r[1] for r in conn.execute(text("PRAGMA table_info(search_prefs)"))]
if "distance" not in sp_cols:
    conn.execute(text("ALTER TABLE search_prefs ADD COLUMN distance INTEGER"))
💡 Jr dev note — what’s a “migration”? When you add a column to a table, databases that already exist won’t magically have it. A migration is code that brings an old database up to the new shape. The pattern here — “check if the column exists, add it if not” — is safe to run every startup: the first run adds the column, every run after that does nothing. We copied this pattern from the existing migrations right above it.

What we did not touch (next ideas)

  • Small towns. geonamescache only knows larger cities (~3,400 of them). A job in a tiny suburb that isn’t in the dataset falls back to the in-state text match rather than precise distance. Swapping in a fuller city dataset behind the same src/geo.py functions would fix that without touching anything else.
  • Remote-only searches ignore the radius on purpose — every result is remote, so distance doesn’t apply.
  • 0 miles currently means “same city center,” which is a reasonable “exact” setting but blunt; a future tweak could make low values a touch more forgiving.
