📋 Job History — what changed & why

Where the "Apply" page went, and how the app now keeps a record of every job you saved and every job you applied to.

The 30-second version. The sidebar entry that used to say Apply now says Job History. It holds two lists side by side: Applied — every job you've submitted, each one marked Pending, In-process, Accepted or Rejected, with a coloured ring round the card so you can read the whole list at a glance — and Saved Jobs, which is everything you hit the new 💾 Save button on over in Job Search. The old auto-fill page has been switched off, not deleted.

Why the Apply page went away

The Apply page had one real feature: Launch Auto-Fill opened a Chromium window, walked every text box on the application form, and typed in whatever it could recognise from your profile — name, email, phone, LinkedIn.

The trouble is that a real job application is mostly not text boxes. It's dropdowns ("How did you hear about us?"), checkboxes, radio buttons, and — the big one — a file upload for your résumé. Auto-fill handles none of those. On a Workday or Greenhouse form it would fill four easy fields and hand you back something that still needed ten minutes of work, with no résumé attached. It was taking up a top-level slot in the sidebar without earning it.

It has not been deleted. The page moved to archive/4_Apply.py, byte for byte. Streamlit builds the sidebar out of whatever files it finds in the pages/ folder, so moving the file out of that folder is the whole mechanism — nothing was commented out or rewritten. The engine behind it, src/autofill.py, wasn't touched at all.

Bringing it back is one command: git mv archive/4_Apply.py pages/4_Apply.py. See archive/README.md for the two loose ends to reconnect if you do.

The life of a job, end to end

You find it — Job Search

Every listing now has a 💾 Save button. It used to say "Auto-Apply" and would fling you over to the Apply page; now it quietly keeps the job and shows a small toast. Nothing navigates, so you can save five jobs in a row without losing your place in the results.

It waits — Job History › Saved Jobs

Saved jobs land here with the match score and the one-line reason the AI gave when it found them, so you can make the call later without re-running the search. Two buttons: ✓ Mark as applied and 🗑 Remove.

You apply — it moves lists

Marking it applied moves the job out of Saved Jobs into the Applied tab, stamps the date, and sets it to Pending. (You can still mark a job applied straight from Job Search, exactly as before — that skips the middle step and lands in the same place.)

You keep score — Job History › Applied

Four buttons on every card. Press one and the card's colour changes. The button for the status you're already on is greyed out, so the four options stay in the same place on every card and you can see where a job stands without reading anything.

The four statuses

StatusColourWhat it means
Pending Amber #F59E0B Applied, heard nothing yet. Every job starts here — you never have to set it.
In-process Yellow #EAB308 Something is happening. A note box appears on these cards only, for recording which round you're on — "Round 2", "Onsite", "Take-home due Friday".
Accepted Green #22C55E You got it.
Rejected Red #EF4444 Closed out. No longer worth thinking about.

How the colour actually gets onto the card

Streamlit doesn't let you set a border colour on a container. What it does do is put a CSS class on any container you give a key to: a container keyed histcard-accepted-14 comes out in the HTML carrying the class st-key-histcard-accepted-14.

So the colour isn't applied to the card at all — the card's key is built out of its status, and one stylesheet at the top of the page paints anything whose class contains st-key-histcard-accepted- green. Four rules, one per status. It's the same trick the Job Search page already uses to outline a posting with hidden AI instructions in red, so this is a pattern the codebase had rather than a new invention.

Why every card also says its status in words. The ring depends on the exact shape of Streamlit's HTML. If a future Streamlit release changes that markup, the rings silently stop appearing — no error, nothing in the logs. The text badge (🟡 In-process) is deliberately redundant, so the failure mode is "the colours are gone", not "I can't tell what any of these are". Colour is never the only thing carrying the meaning — which is also just how it should be for anyone who doesn't easily tell amber from yellow.

Your existing 25 applications didn't need touching

There was an earlier version of this tab with a different set of statuses — Interview, Offer, Accepted, Declined. Two of your rows are still marked declined from it, and the other 25 were never given a status at all, so they sit empty.

Rather than rewriting that old data — the kind of one-way migration that goes wrong at 2am — there's a single function, normalize(), that every read passes through: 

# src/application_status.py
None or ""   → pending      # never given a status
"interview"  → in_process   # the old vocabulary
"offer"      → in_process
"declined"   → rejected
anything else → pending      # never break the list over one odd cell

The old rows read correctly, nothing was overwritten, and if you ever restore an older backup it still works. Your two declined rows show up as Rejected.

Built so the Excel export is easy later

You mentioned wanting this hooked up to a spreadsheet or a database eventually. Worth saying plainly: it's already in a database. Everything lives in data/jobseeker.db, a SQLite file sitting in the repo — SQLite is a real database that happens to be one file instead of a server. What's actually missing is an export. Four small things were done now to make that easy, because all four are painful to add afterwards:

WhatWhy now and not later
to_application_record() One function that turns a database row into a flat, tidy record with stable column names. The export becomes about three lines on top of it, and nothing else in the app has to know what the spreadsheet's columns are called. pandas, which writes Excel files, is already installed.
status_updated_at Every status change is now timestamped. A sync that runs more than once needs to know what changed since last time, and a timestamp is the one thing you genuinely cannot work out after the fact — if you don't start recording it today, that history is simply gone.
Pending is stored, not implied A newly applied job gets the actual word pending written to it rather than being left blank. Every exported row then has a value in every cell, instead of a spreadsheet full of holes you have to explain.
One vocabulary file The four statuses, their labels and their colours are defined in exactly one place, src/application_status.py. A spreadsheet's dropdown can be built from the same list the app renders, so the two can't drift apart.

What's next, if you want it

  • Export to Excel — a Download button on the Applied tab. The groundwork above is most of the work.
  • A "Saved" marker in Job Search — right now Save shows a toast and then the listing looks the same as before, so on a long results page it's easy to lose track of what you already kept.
  • Follow-up nudges — with applied_at and status_updated_at both recorded, "still Pending after 14 days" is a question the data can now answer.
  • Auto-fill, properly — dropdowns and résumé upload are what it would take for archive/4_Apply.py to earn its place back.
