🎯 How we made job matching work like an ATS

JobSeeker · a walkthrough of the matching rework, written for a junior dev

TL;DR — The matcher used to feed the AI only the first 300 characters of each job description, so it never saw the “Requirements” section and couldn’t really judge fit. We now read the full description, ask the AI to do an ATS-style keyword check (what’s required vs what’s on your résumé), flag deal-breakers, and turn all of that into one transparent score. We also made scoring ~8× faster by running the AI calls in parallel instead of one-by-one.

First, what’s an “ATS”?

An Applicant Tracking System is the software companies use to screen résumés. When you apply, your résumé usually doesn’t go straight to a human — the ATS scans it first and asks: does this person have the skills and requirements we listed? It mostly does this by keyword matching (does the résumé mention “Kubernetes”, “5 years”, “Bachelor’s degree”, etc.) and filters out the ones that don’t clear the bar.

Our app does the mirror image: instead of scoring one résumé against one job, it scores your one résumé against many jobs, so you can see which postings you’d actually match. To be useful, it needs to think the way an ATS thinks.

The core problem root cause

src/job_matcher.py — the old code that built the prompt

# For each job, this is the text we sent to the AI:
f"Title: {j['title']} | Company: {j['company']} | "
f"Description snippet: {str(j.get('description', ''))[:300]}"
                                                  ↑ only the first 300 characters!

On almost every posting, the first 300 characters are fluff — a one-line intro and some company marketing. The part that actually matters (“Requirements”, “Qualifications”, “Must have…”) lives further down. So we were asking the AI to judge fit while hiding the exact section that describes the job. It was guessing from the intro paragraph.

💡 Jr dev note — why 300 chars is so little 300 characters is about two sentences. A real job description is usually 2,000–5,000 characters. some_string[:300] in Python means “give me characters 0 through 299” — a slice. It’s cheap and easy to write, which is probably why it was there… but it threw away ~90% of the posting.

The new scoring pipeline

Here’s what happens now when you hit Search and a job gets scored:

1 · Read the whole posting
We send up to 3000 characters of the description (was 300) so the requirements section is actually included.
↓
2 · Ask the AI for a structured breakdown — not a vibe
✓Instead of “give me a number”, we ask it to return specific fields per job: how many required keywords you have, which ones you’re missing, and whether you clear hard requirements.
↓ the AI replies with JSON like the object below
3 · The AI’s answer (one job)
"ats_coverage": 71,            # % of required keywords you have
"matched_skills": ["Python", "AWS"],
"missing_skills": ["Kubernetes", "gRPC"],
"title_fit": 80, "seniority_fit": 60, "education_fit": 100,
"knockouts": [],          # hard requirements you FAIL (empty = none)
"reason": "Strong backend overlap; lacks container keywords"
↓
4 · We compute the final score (not the AI)
✓Python blends those fields into one 0–100 number with fixed weights, then applies the knockout rule. See below.
💡 Jr dev note — why let Python do the math? LLMs are great at reading and judging (“is Kubernetes required? is it on the résumé?”) but flaky at arithmetic and consistency. So we let the AI produce the ingredients (the sub-scores) and let plain code do the recipe (the weighted average). The math is now predictable, easy to unit-test, and we can re-tune the weights without re-prompting the AI.

How the final score is built

src/job_matcher.py → _blended_score()

final = (
    0.50 * ats_coverage   # keyword match matters most — this is the ATS part
  + 0.15 * title_fit       # does the role/title line up?
  + 0.20 * seniority_fit   # right level for your years of experience?
  + 0.15 * education_fit   # do you meet stated degree/cert needs?
)
if knockouts:                 # a hard requirement you clearly fail…
    final = min(final, 40)     # …caps the score at 40, no matter what

Worked example

coverage 80 · title 60 · seniority 70 · education 100

0.50·80 + 0.15·60 + 0.20·70 + 0.15·100
= 40 + 9 + 14 + 15 = 78 / 100

The “knockout” idea

A posting says “requires active security clearance” and you don’t have one. Even if everything else is perfect…

capped at 40  ⚠ shown with the reason, but kept in the list so you still see it.

💡 Jr dev note — temperature = 0 We added temperature=0 to the AI call. Temperature controls randomness: high = creative/varied, 0 = “give me your single most likely answer every time.” For scoring we want repeatable results — searching the same job twice should give the same score, not a number that wanders by ±10 each run.

What you see in the app now

All that structured data isn’t just internal — it shows up on each result card:

  • 📊 ATS keyword coverage: 71% — the headline “would this pass a keyword screen?” number.
  • Missing keywords: Kubernetes, gRPC — the most actionable bit. These are words to consider adding to your résumé (if true!) before applying.
  • ⚠ Knockout: requires 10+ yrs — a clear deal-breaker flag.
  • “Match breakdown” expander — the title / seniority / education sub-scores and the keywords you already match.

The blended score still drives the color chip and the “minimum match score” slider, so nothing about how you filter results changed — the numbers behind it are just smarter now.

The speed fix — score jobs in parallel ~8× faster

Reading the full description made each AI call heavier, and we were making those calls one after another. Jobs are scored in batches of 5, so 50 jobs = 10 batches. The old code waited for batch 1 to come back before even starting batch 2:

src/job_matcher.py → rank_jobs()

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=8) as pool:
    # kick off ALL batches at once instead of waiting between them
    futures = {pool.submit(_score_batch, client, profile, batch): batch
               for batch in batches}
    for future, batch in futures.items():
        try:
            comps.extend(future.result())   # collect each batch as it finishes

💡 Jr dev note — “but Python can’t do real threads?” You may have heard about the GIL (Global Interpreter Lock) — Python can only run one line of Python code at a time. The trick here is that scoring is I/O-bound: 99% of the time is spent waiting on the network for Groq to reply, not running Python. While one thread waits, the others can fire off their requests. Threads are perfect for waiting; you’d only need processes for heavy CPU work. We cap it at max_workers=8 so we don’t hammer the API with dozens of requests at once.
